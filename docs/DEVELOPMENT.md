# RESPeCt — developer notes

A decompilation of *Resident Evil Survivor* (PlayStation, NA, `SLUS-01087`),
aimed at a native PC port with full keyboard and mouse controls.

**This repository contains no game code or data.** You need your own copy of
the game. Everything taken from the disc lives in `disc/`, `asm/` and
`build/`, which are ignored by git.

## Disc layout (code)

| File | What it is |
| --- | --- |
| `SLUS_010.87` | Boot stub. Initializes hardware and loads `KERNEL.BIN`. |
| `KERNEL.BIN` | Main program, PS-X EXE, loaded at `0x80010000` (entry `0x80010B08`). |
| `ENEMPROG.BIN` | Bundle of 30 enemy overlays (IDs 34–64): 15 enemies, each built for two slots. |
| `STAGPROG.BIN` | Bundle of 18 stage overlays (IDs 15–32), loaded into the stage slot. |
| `TEST.BIN` | Main in-game module, despite the name. Loaded in slot 0 during gameplay. |
| `TITLE.BIN` | Title-screen overlay in slot 0; one file with four entry points. |
| `TYPEW`, `SCORE`, `STAFF`, `OPTION`, `DEBUG` | Other slot-0 overlays (not split yet). |

`KERNEL.BIN` layout: read-only data `0x800–0x1300`, code `0x1300–~0x48EC8`
(about 290 KB), then data that is 96% zero-filled buffers. Global pointer is
`0x80062D1C`. The Sony library version tags date from 1997–1998 (Psy-Q 4.x era).

## Overlays

`KERNEL.BIN` keeps a table of overlay slot addresses at `0x80010040`:

| Slot | Address | Used by |
| --- | --- | --- |
| 0 | `0x8006C118` | title/menu overlays, and `TEST.BIN` (the in-game module) |
| 1 | `0x800F2C50` | stage overlays (`STAGPROG` 15–31) |
| 2 | `0x800F8000` | enemy slot A (`ENEMPROG` 34–48) |
| 3 | `0x80100000` | enemy slot B (`ENEMPROG` 50–64) |
| 4 | `0x800C3E48` | end of `TEST.BIN` when loaded in slot 0 |

Slot-0 overlays are loaded by `func_80012F8C` from a table at `0x80059618`.
Each entry is a disc position (minute/second/sector in BCD), a sector count
and an entry point inside slot 0.

Inside `ENEMPROG`/`STAGPROG`, each overlay starts on a 2 KB sector with its ID
word. Some follow it with a table of entry points, others go straight into
code, so overlays are found by their rising ID sequence (`tools/overlays.py`).
Load addresses were checked by confirming that every internal `jal` lands on
a function start, and with a RAM dump from DuckStation
(`tools/locate_overlays.py`):

- Stage 15–31 at `0x800F2C50`. Stage 22 also confirmed from a RAM dump in the
  first area.
- Enemy 34–48 at `0x800F8000`, enemy 50–64 at `0x80100000`. Each of 50–64 is
  the same enemy as the one 16 IDs lower, rebuilt for the second slot, with
  identical call-check scores.
- Enemy 40 and its twin 56 only partly fit (8/15 calls) in the same pattern;
  placed at their slots but worth re-checking.
- **Stage 32** has a different header (a file path, like `TITLE.BIN`) and is
  kept as raw bytes until its load address is known.

Overlays in the same slot share addresses, so symbol names carry the overlay
(`func_800F81B0_ovl34`). Configs are generated by `tools/gen_overlay_yaml.py`.

## Input

The controller code lives in KERNEL (`0x80013260–0x80013DD8`) on top of Sony's
`libpad`. It was found from a RAM dump: the port 1 receive buffer at
`0x800633F8` held `00 41 FF FF` (digital pad, nothing pressed).

- `pad_Init` registers both receive buffers with `PadInitDirect`, starts
  communication, sets up vibration buffers, and stores buffer pointers in
  `g_padBuf1Ptr`/`g_padBuf2Ptr`.
- `pad_Update` runs each frame: connection state and controller type per port.
- `pad_GetButtons` returns bytes 2–3 of each port (active-low; `0xFFFF` = no
  buttons or no pad).
- `pad_GetAxes(port)` returns pointer/axis data through `g_padAxesHandlers`,
  one handler per controller type: **PlayStation Mouse** (X/Y motion),
  **GunCon** (X/Y screen position), DualShock and analog joystick (sticks),
  NeGcon. Digital pads return 0. The GunCon reader is still present in the NA
  build, so its removal happened higher up.

In TEST.BIN, `input_SampleFrame` stores `pad_GetAxes` into `g_inputAxes` each
frame and passes `pad_GetButtons` through `input_MapButtons` (probably the
button config) into `g_buttons`. While `g_inputLocked` is set the buttons are
zeroed (probably cutscenes); in attract mode, input is replayed from
`g_demoInput` instead.

## Player control (original)

Tank controls, in TEST.BIN:

- `player_Update` runs each frame (unless `g_playerFrozen`): calls
  `player_Control`, adds `g_playerYawVel` to the player's heading (`g_player`
  +0x46, 4096 = 360 degrees), and when walking moves the player along the
  heading at `g_playerMoveSpeed`, through `move_Collide`, with a walk, run or
  backstep animation.
- `player_Control` sets `g_playerMoveFlags` from the pad: forward/back, turn
  left/right (with a ramp up to 10 frames), run while another button is held.
  It has separate paths for digital pad, DualShock analog and **GunCon** (point
  off-screen and press a button to walk), so GunCon gameplay code is still in
  the NA build.
- Holding the aim button stops movement and runs `player_AimMode`: a 2D reticle
  (`g_reticleX/Y`, centred at 160,120 on entry) moved by d-pad or stick; pushing
  it against a screen edge turns the view. Fire calls `fire_AtScreen` with the
  reticle position.

The modern FPS controls replace `player_Control`/`player_AimMode`: free
movement and strafing while aiming, mouse-driven heading, and firing at the
screen centre through `fire_AtScreen`. Collision and animation stay as they
are.

For the PC port this is the hook: keyboard state feeds `pad_GetButtons`, and
real mouse motion feeds `pad_GetAxes` through the mouse handler's format.

## Testing changes in DuckStation

Changed code is tested as DuckStation memory patches, without rebuilding the
disc image. TEST.BIN always loads at `0x8006C118`, so `tools/mkpatch.py` diffs a
modified TEST.BIN against the original and writes GameShark codes to a
`SLUS-01087.cht` file for DuckStation's `patches` folder. Every write is
guarded by `D006C118 0006` (TEST.BIN's first word), so nothing is written while
the title screen or a menu overlay occupies the slot.

First check (confirmed in game): doubling the walk speed at `0x80077490`.

C replacements: `tools/build_mod.py` compiles `src/mods/<function>.c` with
clang for the R3000 (`-Oz`, MIPS I), links it at the original entry address
with every game symbol resolved, checks it fits, and splices it into a copy of
TEST.BIN for `mkpatch.py`. `player_AimMode` was rewritten this way to behave
exactly like the original; confirmed in game with no difference.

## Setup

1. Copy these files from the root of your disc into `disc/`:
   `KERNEL.BIN`, `SYSTEM.CNF` and the overlay `.BIN` files listed above.
2. Install the tools:
   - Python 3.11+ with [splat](https://github.com/ethteck/splat) (`splat64[mips]`)
   - LLVM 18+: `clang`, `ld.lld`, `llvm-objcopy`
3. Split the binary, then rebuild and check it:

```sh
python3 -m splat split kernel.bin.yaml
python3 -m splat split enemprog.yaml
python3 -m splat split stagprog.yaml
./build.sh      # prints "OK: ... matches disc/..." for each file
```

## Why LLVM instead of GNU binutils

The build uses LLVM's assembler and linker so it runs anywhere clang does.
LLVM is missing a few PS1-specific pieces, which two small tools cover without
changing a single output byte:

- `tools/llvm_fixup.py` turns coprocessor-2 (GTE) instructions and `rfe` into
  raw `.word`s, using the bytes splat prints beside each instruction.
- `tools/llvm_ldscript.sh` replaces splat's catch-all `/DISCARD/` rule, which
  `ld.lld` rejects, with an explicit list of metadata sections.
- `include/llvm/macro.inc` drops `.aent` (debug-only) and defines `cop2`.

This is fine for the functional decompilation this project is doing. A strict
byte-matching decomp would want the original compiler and GNU as.

## PC port (`port/`)

The game runs natively: `tools/recomp/recomp.py` translates every module's
machine code to C (`port/gen/`, generated from your disc, not in git) and
`port/src/` provides the PlayStation underneath it:

| File | What it does |
| --- | --- |
| `rt.c`, `bios.c`, `thread.c` | CPU state, calls into overlays, BIOS services, threads and interrupts as coroutines |
| `gpu.c`, `render.c` | GPU commands; rasterizer for the PS1's VRAM and a 1-4x high-resolution copy (worker threads) |
| `render_gpu.c`, `render_gpu.hlsl` | The same high-resolution drawing on the graphics card (Direct3D 11 compute shaders), up to 8x |
| `gte.c` | Geometry coprocessor, with fractional screen positions, depths and models' matrices in full precision kept for the renderer |
| `cdrom.c`, `iso.c` | CD drive and file system on the `.bin` image |
| `spu.c`, `mdec.c` | Sound (voices, reverb, XA streaming) and movie decoding |
| `card.c`, `sio.c` | Memory cards (`.mcd` files) and controller port |
| `config.c` | `resurv.ini` settings |
| `main_win32.c`, `main_headless.c` | Windows front end; headless runner for testing (PNG frames, WAV) |

`port/decomp/` holds hand-written C that replaces translated functions
(listed in `tools/recomp/native.txt`):

| File | What |
|---|---|
| `player.c`, `camera.c` | Player controls (FPS mode), movement, camera pitch and recoil |
| `hud_panels.c`, `hud.h` | HUD panel pool, panel callbacks, bullet row, reload start, panel animation |
| `weapon_view.c` | Per-weapon view handlers (shots, casings) and reload animations |
| `inventory.c` | Item list removal, weapon sound bank / shot sound |
| `gameflow.c` | Per-frame flow handlers, game over and continue, enemy grabs, player hits, footsteps |
| `mainloop.c`, `checkpoint.c` | TEST start-up, entering rooms, input sampling (and the attract demo), the work heap, room script branches; making and restoring the checkpoint |
| `render.c`, `models.c`, `libgs.h` | Ordering tables, model sorting, shadows, frame flip, textures, display set-up; binding models and their polygon/animation drivers |
| `shooting.c`, `combat.c` | Resolving shots against enemy hit boxes, blood, the reticle test; weapon stats and damage |
| `collision.c`, `anim.c` | Wall and line collision, moving through it (`move_Collide`); animation tracks and coordinate updates |
| `enemy.c`, `zombie.c`, `licker.c` | Shared enemy code (steering, awareness, pushing apart, attacks, aim targets); the zombie (ENEMPROG 50) and licker (53) programs |
| `stage.c`, `stage22.c`, `stage23.c` | Stage start/run/update, screen flash; the first area's rooms (flames, smoke) and stage 23 |
| `sound.c` | Sound cues, positional enemy sounds, bank loading, streams |
| `message.c` | Message windows, text and font |
| `room_change.c`, `room_load.c`, `room_loader.c`, `room_triggers.c`, `screen_fade.c` | Doors and room changes, room objects, the background loader (models, textures, sounds, items), walk-in triggers, fades |

| `hud.c`, `cheats.c` | Port additions: weapon HUD image cache, cheats, weapon hotkeys |

Each decompiled function is checked against the translated original with
`tools/eq/run.sh BASE NEW OUT`: seventeen input scenarios (new game, weapon
cycling, walking and fighting, the status screen, ammo running out,
launchers, reloads, zombie fights, a door, dying and continuing, saving at
the payphone, loading a saved game) replayed with both builds, RAM compared
every 50 frames (outside the stacks) plus screenshots.
`tools/eq/coverage.sh` lists decompiled functions the scenarios never reach,
`tools/eq/sscompat.sh` checks save states made before a change still
continue identically, and `tools/eq/profile.sh` lists the translated
functions the scenarios run (what to decompile next). How to decompile a
function: `port/decomp/README.md`.

Build: `python3 tools/build_mod.py && python3 tools/recomp/recomp.py`, then
`make -C port` (Linux headless) or `make -C port win` (Windows, with clang
and a MinGW-w64 sysroot in `~/toolchain/sysroot`).

### Release build (no game code in the exe)

The translated build is made from the player's disc, so it can't be handed
out. The release build (`make -C port dist` for Linux headless, `make -C port
windist` for Windows, `make -C port release` for the download zip, `RESPeCt.zip`) has no
`port/gen` at all: `port/src/interp.c` runs the game's own code from RAM,
where the game loads it from the player's disc, following exactly the rules
the recompiler translates by, so both builds behave identically (`tools/eq`
compares them like any other change; decompiled functions run as native C in
both). What the interpreter needs to know about the code (function extents,
how each jump was translated, jump tables, the port's own mod patches) is in
`port/meta/meta.c`, written by `tools/recomp/meta.py` from the same analysis:
addresses and hashes only. Overlays are told apart by a hash of their first
bytes instead of the bytes.

The disc image can be a `.bin`/`.cue`, `.img`/`.ccd` or `.chd` (libchdr, in
`port/third_party/`). It's checked against the USA disc's file layout and a
hash of every file holding code (`port/src/disc_ids.h`, from
`tools/disc_ids.py`). On Windows the first run looks next to the exe (and a
level or two below) for an image, unpacks a `.zip` into `disc/`, and tells
the player what's wrong with anything unusable (`port/src/setup_win32.c`).
`tools/audit_exe.py EXE` confirms an exe holds no 32-byte run of the disc.

### Save states

F5 saves the whole running game to the selected slot (1-99) and F9 loads it
(F6/F7 or the Saves page of the F1 panel pick the slot, which starts on the
one saved last; files go in `saves/` next to the exe). The translated code resumes at the saved instruction: every function
has a resume switch over its call return addresses and loop polls
(tools/recomp/recomp.py), and loading re-enters the innermost function, then
each caller in turn by its return address (port/src/savestate.c). Memory
cards are not part of a save state.

### Saved games (payphones)

The game's own memory card save only keeps the weapons collected (offered
after dying; LOAD GAME then starts the story over with them). Using a
payphone (left click) opens that same save screen; the port also writes the
game's progress checkpoint and where the player stood to
`saves/card1-BASLUS-01087-NN.sav`, next to the card save, and then carries on
from the phone. When the title screen's LOAD GAME loads a card save that has
such a file (and the card save is unchanged since), the game resumes there
(port/decomp/savegame.c).

The title's memory card list goes through libapi's `firstfile`, which looks
the card device up in the BIOS's device table in low RAM; the port's HLE BIOS
has none, so it is replaced (kernel 80039C58) to call the BIOS directly.

### Cutscenes, movies, sound

Holding Space fast-forwards door transitions, scenes where the player has no
control (TEST running, 0x80062DEC clear, status screen 0x80063B5C closed) and
movies (the MDEC decoded a picture in the last few frames). Movies are
deblocked and scaled up bicubically to the internal resolution
(port/src/display.c). The SPU lets at most N voices (Audio page, default 3)
play one sample at once: a swarm of bugs keys the same one-shot sound on all
16 voices; the PlayStation behaviour (no limit) is 0 and the headless default.

With "Steady 3D", a corner's exact projected position is found by the RAM
word the GTE stored it in (port/src/gte.c); looking it up by its pixel alone
mixed up about one corner in eight on small, distant models.

### Steady 3D and the depth fix at high resolutions

What makes models tremble at 4x and up, and what port/src/gte.c does about
it (the high-resolution picture only: everything the game reads stays the
GTE's own integers):

- Each part of a model is drawn with its own matrix, which libgs's GsGetLs
  builds through the GTE with a cut to whole units at each step. The same
  chain is multiplied out in double precision (hook on the call, interp.c)
  and goes with the matrix when the game loads it (SetRotMatrix,
  SetTransMatrix): corners, and their depths, come from it.
- NCLIP (keep or drop a face) takes its sign from the corners' fractions:
  on whole pixels a distant model's tiny faces came and went as the camera
  turned (129-151 of a zombie's 156 triangles drawn, now all of them).
- Corners a fraction of a pixel apart are not welded together any more,
  and the pass that filled background between a model's parts is off: with
  the matrices exact the seams meet, and both moved outlines by a few
  pixels from frame to frame.
- The depth fix knows which model a polygon belongs to (the root of its
  coordinate chain): a model's parts hide each other 2 units behind; other
  objects keep the PS1's order, so a model reaching into another (a hand
  through the floor) is drawn as on the PS1 at any distance. (A threshold
  measured along the view, as before, grows with the distance and the
  slant: hands sank into the floor more or less as you walked.)

The bench checks all of this on recorded frames: `RT_INT_MATRIX`,
`RT_INT_NCLIP`, `RT_INT_Z`, `RT_WELD`, `RT_HOLES`, `RT_DEPTH_TOL`,
`RT_CROSS_TOL` bring back the old behaviour for comparisons.

### Graphics card

With `graphics_card = 1` the queue render.c's worker threads run goes to the
card instead (port/src/render_gpu.c): render_gpu.hlsl runs the same code as
raster_tri, raster_rect and run_ops, one thread per pixel, each pixel's
operations in the queue's order (binned to 16x16 tiles), edges in double
precision so they come out exactly as the CPU's 64-bit integers. The
picture shown is made there too (24-bit colour, brightness, Close model
gaps) and at the window's size, shrunk by area. The PS1's own VRAM stays on
the CPU (the game reads it); the card gets a copy with every batch for
textures. Replacement images are copied into a separate RGBA8 shader
buffer and referenced by each primitive's original texpack mapping. The
shader mirrors the CPU's bilinear sampler, atlas bounds, alpha classes,
lighting and PS1 blend modes. Native VRAM and the texture matcher are
unchanged. Image identities are shared within a synchronized drawing queue
and reset before texpack_frame can evict decoded images. GPU transfers are
bounded to 128 MiB per queue; allocation failure or a larger queue uses the
original texture and logs a warning. The CPU staging arena and GPU buffer
retain their capacity for reuse.

An old save state without tracked texture uploads still needs a room load
before its textures can match the pack, on either renderer. This change
does not reconstruct those missing upload records.

`port/tests/run-gpu-hd.ps1` builds and executes the production CPU/D3D11
rasterizers with synthetic images (no game assets). It checks rectangles,
triangles, alpha thresholds, blending, lighting, atlas limits, perspective,
multiple images and cache renewal at 2x, 3x and 4x, with HD on/off and
24-bit colour on/off. Native VRAM and STP must match exactly; filtered
24-bit RGB permits at most one rounding step. A usable D3D11 device with
double precision is required (exit 2 means unavailable). This does not
replace testing the real pack and gameplay.

Validation of GPU HD support: 158 synthetic CPU/GPU comparisons passed.
Three filtered Gouraud cases differ by one RGB level in a few pixels,
within the declared rounding tolerance; STP and native VRAM match exactly.
A controlled 21-frame arcade-room replay with the real pack at 2x produced
an identical CPU HD/GPU HD displayed frame and identical native VRAM with
HD on and off. GPU HD was also observed in the Windows frontend at 8x.
Interactive F2 and live renderer switching with HD, other hardware, and
full-game pack compatibility remain unverified by these checks. Actual
allocation failure during buffer growth has not been fault-injected.

Frames from
the headless runner with `RT_GPU=1` are identical to the CPU's;
`RT_GPU_AT=frame:on` switches while running, `RT_SHOW=w,h` makes the picture
at a window's size.

### Field of view

The FOV setting changes the GTE's projection distance while TEST runs
(port/src/gte.c). Where the game turns a screen position back into a 3D
point (the shot's flash and impact, test 8009B71C) it runs with the game's
own projection: native.txt can name a wrapper (`~name`) that runs around the
translated original instead of replacing it.
